Manzar · rendering architecture · August 2026

Stop handing whole images to the webview

Manzar decodes every pixel of every file in the browser engine, then asks it to re-raster the whole surface on each zoom step. Measured against a Rust pipeline that decodes and scales only what the window can show: opening a file gets 5–8× faster, peak memory drops up to 11×, and a zoom step stops costing anything at all.

Measured on Toolchain Window Harness benches/render-bench

Where the cost comes from

The pipeline as it stands

Manzar's Rust side is already careful. The registry hands out opaque ids instead of paths, video streams through io::copy so memory stays flat, and oversized files are gated before they are served. The cost is not sloppiness — it is the division of labour. Rust reads bytes; the engine does all the pixel work, at full resolution, with no idea how big the window is.

How the engine's side was measured

WebKitGTK cannot be driven from a benchmark harness, so the engine's work is modelled: a full-resolution decode with a production Rust decoder, then a full-surface rescale. That model charges the webview for the decode and the scale and nothing else — not the protocol copy, not the source surface it keeps alongside the decoded one, not the per-frame texture upload. The engine's own decoders (libjpeg-turbo, libpng) are in the same performance class as the ones used here. The comparison is therefore conservative: the shipping path costs at least this much.

Evidence

Zooming stops scaling with the image

This is the structural result, and it matters more than any single multiple. A compositor asked to scale a promoted layer re-rasters the layer — all of it, including everything outside the window. A renderer that owns its own pixels works out which source rectangle the window is looking at and resamples just that, straight into a window-sized buffer.

Evidence

Fit-to-window, and the decode underneath it

Scaling is where the largest drop-in gain lives. It needs no new architecture, no protocol change and no GPU: one crate, called on a buffer Manzar already has.

Why the curve flattens

Entropy decoding is not skippable. The Huffman pass still has to walk every coefficient block in the file to find the ones it keeps, so DCT scaling only removes the back half of the decode — the inverse transform, chroma upsampling and colour conversion. That sets a floor of roughly 240 ms on a 61 MP frame no matter how small the output is. Scaled decoding is worth taking, and it is not where the headline win comes from.

Negative results

What the measurements rule out

Two changes that look obviously worth making are not, and both would have cost a week.

Do not swap the JPEG decoder

image 0.25 already depends on zune-jpeg 0.5.15 — it is the JPEG backend, not an alternative to it. Calling zune-jpeg directly measures at 1.0×, because it is the same decoder either way. The gain that a decoder swap appears to promise has already been banked; what is left on the table is the scale it is asked to decode at, and everything downstream of it.

The plan

Four phases, in dependency order

The phases are numbered because they are a real sequence: each one is worth shipping alone, and each one makes the next smaller. Phase 0 is a week and banks most of the measured win. Phase 3 is the only one that needs a decision Manzar has not already made.

Phase 0

Move scaling into Rust

~1 week · no architecture change

Nothing about the process model changes. The custom protocol, the approved-id registry and the oversize gate all stay exactly as they are — the response body just stops being the original file. This is where the bulk of the measured gain is, and it is reversible in an afternoon.

  • Add fast_image_resize and jpeg-decoder to src-tauri/Cargo.toml. Keep image: it stays the decoder for everything that is not JPEG, and its JPEG backend is already the fast one.
  • In core/image_protocol.rs, replace std::fs::read for images with a decode-and-fit: probe the header, pick the DCT scale that covers the fitted size, resample to the window, encode once for transport.
  • Pass the window size from the frontend. App.tsx already knows it; the protocol URL needs one more segment, or the snapshot command needs one more field.
  • Keep the full-resolution path behind the existing oversize gate, so “actual size” on a modest image is unchanged.
  • One line in core/media_server.rs: stream.set_nodelay(true) on each accepted connection. Measured at 1.5× on sequential range requests.

Phase 1

Rust owns the pixels, and keeps them

~2–3 weeks · new module, same process model

Phase 0 still decodes on every navigation and still cannot make zoom cheap, because it holds nothing between requests. Phase 1 adds the piece that does: a decoded frame kept in Rust with a small mip pyramid over it. Zoom and pan become a crop and a resample of the visible rectangle — the operation whose cost the measurements show is flat in the image size.

  • A core/render_cache.rs holding the current frame plus its neighbours, bounded by bytes rather than count, evicting on navigation.
  • Serve a viewport tile per request: id, zoom, pan offset. Zoom stops being a CSS transform and becomes a request, so the engine never re-rasters a promoted layer.
  • Drop will-change: transform and the scale() transform from .viewer-image--manual. They are what currently promotes the image to a layer the compositor must re-raster.
  • Decode the next and previous image in the sequence off-thread while the current one is on screen. Navigation becomes a cache hit.
  • Transport raw BGRA rather than re-encoding to PNG — a window-sized frame is ~9 MB and the encode would cost more than the copy.

Phase 2

Put the frame on the GPU

~3–4 weeks · evaluate before committing

With Phase 1 shipped, the remaining per-frame cost is a CPU resample and a copy into the engine. Uploading the decoded frame as a wgpu texture once turns zoom and pan into a uniform-matrix update and a draw call — sub-millisecond, and free of the copy entirely. The catch is not the rendering; it is where the surface goes.

  • Prototype first, decide second. Compositing a wgpu surface with a webview in one window is the known-rough part of Tauri: the tracked reports describe the webview and the GPU context contending for the surface, with flicker and z-order problems.
  • Two routes worth prototyping: a second transparent always-on-top window holding the GPU surface with the webview as chrome, or a native window host with the webview as a child surface.
  • If neither prototype is clean, stop at Phase 1. It already delivers flat zoom cost; Phase 2 buys smoothness during a drag, not correctness.
  • The same texture path is what Phase 3 needs for video, so a working prototype here is a prerequisite for hardware-decoded playback, not a parallel effort.
Zoom and pan projected: one draw call Risk integration, not rendering
Phase 3

Decode video in-process

~4–6 weeks · depends on Phase 2

Video is the part of Manzar that is least under its own control today. The custom protocol cannot serve it at all — WebKitGTK resolves <video> URIs through GStreamer, which knows nothing of app-registered schemes — so core/media_server.rs exists purely to give the engine an origin it will accept. Every byte of every frame crosses a TCP socket, and the decode happens somewhere Manzar cannot see or tune.

  • Demux and decode in-process, presenting decoded frames as GPU textures through the Phase 2 surface.
  • Retire the loopback HTTP server, the per-connection thread, the token and the DNS-rebinding host check along with it. The security boundary gets smaller, not bigger: no socket means no origin to defend.
  • This also retires the GStreamer plugin matrix the README currently asks Linux users to install by hand.
  • Frame-accurate stepping, thumbnails and a scrubber become possible for the first time. They are not reachable through a <video> element.

Video

What the socket costs

Decode dominates video playback, and decode is exactly what this container has no libraries to measure — there is no FFmpeg, GStreamer or dav1d here. What can be measured is the transport underneath it: the same bytes, pulled through the loopback hop that ships today, against an in-process read.

A stall worth fixing now, and one that cannot be

Isolating the hop found a flat 41.2 ms per request spent waiting for the response head — the signature of Nagle's algorithm meeting a delayed ACK. Setting TCP_NODELAY on the client collapses it to 0.8 ms; setting it on the server does not touch it, but does roughly triple body throughput (149 → 431 MB/s).

Manzar owns the server socket and should set it — that is the one-line change in Phase 0. It does not own the client socket, because the client is the engine. Even with both ends tuned the hop runs at 657 MB/s against 3,691 MB/s for an in-process read. That residue is not a bug to fix; it is the argument for not having a socket.

Caveats

What this does not establish

The engine's side is modelled, not run. No WebKitGTK, WebView2 or WKWebView was measured. The model is deliberately conservative — it omits the protocol copy, the retained source surface and the texture upload — but it is still a model, and the true baseline is unknown rather than merely higher.

The app itself was not built or tested here. This container has no GTK development libraries, so cargo test in src-tauri cannot run. The harness is standalone by design and its own six tests pass. No application source was changed.

Every Phase 2 and Phase 3 figure is projected. Nothing GPU-related and nothing about video decode was measured, because this machine has neither a GPU nor a media stack. Projections are marked in amber throughout; measured results are in blue.

One machine, one corpus. Four cores with AVX2 and AVX-512, on synthetic images built to photographic statistics rather than real camera files. The SIMD gains will be smaller on a NEON laptop; the memory and flat-zoom results are structural and will not be.

Quality was not compared. Both paths were asked for Lanczos3 at identical output dimensions, and a test asserts the dimensions match — but no perceptual comparison was made between a DCT-scaled decode and a full decode scaled down. That check belongs in Phase 0 before it ships.

Reproduce

Running the harness

The corpus is generated deterministically on first run and cached, so a fresh machine and a warm one produce the same figures. Nothing needs downloading.

# every figure on this page, written to report.json
cd benches/render-bench
cargo run --release --bin report

# the same comparisons under criterion, with confidence intervals
cargo bench --bench pipeline

# invariants: aspect ratio, DCT scale never under-resolves, zoom stays
# bounded by the window, both resamplers agree on output size
cargo test --release

# where the loopback hop spends its time
cargo run --release --bin diag

Set MANZAR_BENCH_CORPUS to keep the corpus somewhere other than the temp directory. The 61 MP fixture takes about a minute to generate the first time.
