The viewer stopped handing whole images to the engine

Phase 0 of the native render path is implemented and measured against the code it replaces. Opening a 61 MP photograph is 4.0× faster and the engine is left holding 19× less decoded image. Both figures come from calling the function the application actually serves images through.

Measured on AMD Ryzen AI Max+ 395 · 32 cores · AVX2, AVX-512 Engine WebKitGTK 2.52.6 · GTK3 · Wayland Window 2560×1440 Harness src-tauri/examples/fit_bench.rs

The result

Four numbers, all from the shipping code

4.0× Faster to first pixel Opening a 61 MP photograph: 624.9 ms to 156.3 ms. The win grows with the file.
19× Less decoded image 229 MB down to 11.9 MB of RGBA the engine must hold. Arithmetic, not a model.
2.5× Worst case, still a win PNG has no scaled decode to take, so this is the SIMD resampler working alone.
92 Tests passing 83 before, plus nine covering the fit geometry, every decline, and the query wiring.

Evidence

Opening a file

The journey measured is a file on disk to pixels ready for the window. The Rust half is the real serve_approved_media; the engine's half is modelled, because WebKitGTK cannot be driven from a benchmark harness.

The model charges the engine for a decode of whatever bytes it is handed, plus a scale to the window when those bytes are larger than it — and nothing else. It does not charge for the protocol copy, the source surface kept alongside the decoded one, or the per-frame texture upload. The comparison is therefore conservative in the baseline's favour.

Confirmed in the running application

The figures above are a harness, so the result was also checked by hand: a debug build was launched against WebKitGTK 2.52.6 on Wayland with the 12 MP fixture, and the fitted bitmap decoded and displayed correctly — no corruption, no channel swap, colours intact. A test now pins the wiring underneath it, asserting that ?w=&h= produces an image/bmp surface at 1920×1440 and that its absence still returns the original file byte for byte.

Two things this is not

It is not the projected 5–8.5×. The write-up that argued for this work measured on a four-core container; this machine is a thirty-two core Ryzen where the baseline's scalar resample runs far faster, so the ratio compresses even though both halves got quicker. The direction and the structure hold; the multiple is smaller.

The engine's half is still modelled. No WebKitGTK decode was timed. Only Engine decodes is exact — it is width × height × 4 on the dimensions the engine is handed, and it is the column that matters most for a viewer walking a folder.

Correctness

What fitting refuses to touch

Fitting is an optimisation, so it must never change what the user sees. Every case below declines and serves the original file — the exact path that shipped before this change. Because a decline falls back to the old behaviour, each one is safe by construction rather than by care.

Animated GIF

A fitted still is one frame. Every GIF keeps the whole-file path, so animation survives.

Colour-managed images

A profile that cannot be proved sRGB — Display P3, Adobe RGB — goes to the engine, which colour-manages it. The speedup is traded away exactly where it would cost accuracy.

Zoom and actual size

Both are defined against the image's own pixels, not the window's. They drop the size hint and get the original file, so 1:1 is genuinely 1:1.

Images already inside the window

Nothing to gain and a re-encode could only lose, so anything smaller than the window is passed straight through.

Greyscale and CMYK JPEG

These decode to something other than RGB24. Rather than reinterpret the buffer, the scaled decoder hands them back to the general one.

EXIF orientation — the one that had to be added

The engine applied this for free on the whole-file path. Once Rust owns the decode it has to do the same, or sideways photographs ship sideways. It is applied after decode, before the resample.

The cost

More bytes cross the boundary, and that is fine

The fitted surface is BMP, which is uncompressed. A 12 MP JPEG that used to cross the protocol boundary as 2.1 MB now crosses as 7.9 MB. That is a real regression in one column of the table and it is the honest price of the row beside it.

It is worth paying because the boundary is a memory copy inside one process, not a network. Eight megabytes of memcpy costs about a millisecond against the hundred-plus the fit saves, and the engine then decodes a bitmap rather than an entropy stream. PNG would compress it to a third of the size and cost more than the decode the fit just eliminated.

At 61 MP and for PNG the column moves the other way, and sharply: a 29 MB PNG becomes a 7.9 MB bitmap.

Also shipped

Two one-line changes worth their diff

  • TCP_NODELAY on the media server. Video range requests were paying Nagle's algorithm meeting a delayed ACK on every hop. Measured at 1.5× on body throughput. The larger 79× figure in the original write-up needs the same option on the client socket, which belongs to the engine, so it is not ours to set.
  • gst-plugin-va declared as a dependency. Without it H.264 falls back to avdec_h264 and decodes on the CPU, which is what was happening. Verify that decodebin actually selects vah264dec on a given machine — VA element ranks have moved between GStreamer releases.

Not in this change

Zoom still costs what the image costs

The fitted surface is discarded the moment the request ends, so nothing is retained between requests and a zoom step is still a compositor re-raster of the whole promoted layer. Making zoom cost the window rather than the image needs decoded frames held in Rust with a crop-and-resample per viewport — a larger change, and the next one.

The GPU surface and in-process video decode are untouched and remain unproven. On this target both look cheaper than the original plan assumed: Window::default_vbox() hands over the GTK box the webview lives in, which is a far safer route than a second always-on-top window on Wayland, and GStreamer is already a hard dependency with gtksink installed — so in-process video needs neither FFmpeg nor the GPU work it was thought to depend on.

Reproduce

Running the harness

Fixtures are generated deterministically on first run and cached in the temp directory, or in MANZAR_BENCH_CORPUS. A release build is not optional: every SIMD path here degrades to scalar without optimisation. 

# the table above, written to fit-bench-report.json
cd src-tauri
cargo run --release --example fit_bench

# the fit geometry, the declines, and everything else
cargo test

The modelled half of the comparison is the same conservative model used in rust-renderer-plan.html, which this document answers. The standalone harness in benches/render-bench is unchanged and still measures the pipeline in isolation.
